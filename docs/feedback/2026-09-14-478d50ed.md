## Operator and agent surface

- **The v1.2.0 Windows installer generated launchers without the compiler bootstrap.** Under `setlocal DisableDelayedExpansion`, the Visual Studio path was read inside the parenthesised block that set it, so `VCVARS` was always empty and no `run-tavi.bat` from v1.2.0 called `vcvars64.bat`. Found by the review smoke on the copied file, fixed in v1.3.0 (PR #41), confirmed by a cold run whose two-point PUMA scan compiled. Bit every 1.2 user who lacked a developer prompt; cost this session: none beyond the fix. `setup-tavi-dev.bat` reads the same variable the same way but never uses it.
- **A fresh install's first GUI launch blocks on the instrument picker** until a human chooses; the API does not listen until then. An automated post-install check must pass `--instrument puma` or seed `config/instrument_selection.json`. The generated launchers do not forward arguments, so the seed is the only route from the launcher. Cost: one wasted launch, three minutes. Latent for any future installer acceptance script.
- **The API's liveness route is `/api/v1/health`, not `/status`.** A probe on the wrong route returned 404, which my check treated as "not up". Cost: one wasted launch. The API user guide lists routes; read it before probing.
- **The Windows cold run took 87 s** (measured) with a warm package cache, against the README's 10–20 minutes for a cold network. The map build is the visible pause: no output for its duration; the installer now says so beforehand.
- **`.pytest_cache` and the MSVC/vcvars noise** in the AGENTS.md traps section did not bite; `micromamba run -n tavi-dev` was not needed this session (preflight ran the suite itself, 122 s measured).
